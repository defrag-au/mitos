# Mitos platform deployment

How a dApp builder gets a wasm indexer module from "compiles
locally" to "running inside a deployed mitos host." Targets
**wrangler-deploy-style ergonomics**: a focused build tool, a
focused deploy tool, a typed manifest between them, and a
host-side admin endpoint that accepts the artifact.

Cross-references:
- `MITOS_PLATFORM_V1.md` — the runtime this deployment story
  feeds into; the WIT ABI module artifacts conform to
- `MITOS_COMPANION_PATTERN.md` — paired-deployable thesis;
  this doc is the mitos-side half of `cargo cardano deploy`
- `CARDANO_DAPP_FRAMEWORK_THESIS.md` — broader framework
  framing
- Wrangler / worker-build (Cloudflare) — the reference
  experience this is informed by
- `tools/mitos-admin/` — existing CLI scaffold we extend
  rather than replace
- `tools/capture-block/` — pattern reference for
  HTTP-against-mitos tooling

## What we're optimising for

A dApp builder running their own mitos host (or pointing at a
managed one) should be able to ship an indexer change with one
or two commands, without touching the mitos repo, without
restarting the host, and without learning new operational
concepts beyond "build then deploy."

The wrangler/worker-build split is the model. Concretely:

```bash
# In the dApp's repo:
mitos-build              # produces target/mitos/<module>.wasm + manifest.toml
mitos-cli deploy         # uploads the artifact to a configured mitos host
```

Or as a one-shot:

```bash
mitos-cli deploy         # build then upload, like `wrangler deploy`
```

Both halves run from the dApp builder's laptop. The mitos host
exposes an HTTP admin API; everything goes over that.

## Non-goals (v1)

Calling these out so they don't drift into scope:

- **Multi-user auth.** Single shared bearer token (`MITOS_AUTH_TOKEN`)
  for now; URL shape is forward-compatible with per-module
  ownership but enforcement is deferred. See "Auth roadmap" below.
- **OCI / container-registry distribution.** Modules ship as
  raw `.wasm` over HTTP; OCI is a v2+ option once we have
  multiple deploy targets.
- **Hot-reload of running instances.** Upload replaces the
  running instance (brief restart per subscription); seamless
  hot-swap is a v2+ refinement.
- **CF companion orchestration.** Companion-side `wrangler
  deploy` happens via wrangler itself, possibly chained from
  `mitos-cli`; we don't reimplement the CF deploy.
- **`cargo cardano init`.** Scaffolding new dApps is a separate
  workstream once the deploy story is solid enough to template
  against.

## What ships (the four pieces)

### 1. `mitos-build` — the build tool

A standalone binary in `tools/mitos-build/`. Single
responsibility: take a Rust crate that targets `wasm32-wasip2`
and produces a component conforming to our WIT, validate it
exhaustively, and emit a deployable artifact directory.

```bash
mitos-build --crate indexer
# OR (auto-detected if run from a workspace member with [package.metadata.mitos]):
mitos-build
```

Inputs:
- A path to a Rust crate (or autodetect from CWD)
- Optional `[package.metadata.mitos]` block in `Cargo.toml`
  for module-id, default config path, etc.

What it does:
1. `cargo build --target wasm32-wasip2 --release -p <crate>` (or
   pre-built artifact if given via `--wasm-path`)
2. Component-validate via `wasmtime::component::Component::from_file`
   against a fresh `Engine` — catches malformed components before
   deploy
3. Extract WIT exports/imports via `wasm-tools component wit`
   (or wasmtime's component metadata) and check the world matches
   `mitos:platform/mitos-module`
4. Run a dry instantiation in a sandboxed `Store` and call
   `module-version()` + `trap-policy()` to extract the declared
   ABI version, trap strategy, and retry policy
5. Compute SHA-256 of the wasm bytes
6. Write artifact to `target/mitos/<module-id>/`:
   - `<module-id>.wasm` — the binary
   - `manifest.toml` — auto-generated from the dry-load (see schema below)
7. If a `mitos.toml` exists alongside the crate, copy it in too

Outputs (printed to stdout, machine-readable with `--json`):

```
Module:        my-indexer
SHA-256:       abc123...
Size:          2.3 MB
ABI version:   1.0
Trap policy:   replay (max-retries=3, backoff-cap-ms=1000)
WIT world:     mitos:platform/mitos-module
Artifact:      target/mitos/my-indexer/
```

### 2. `manifest.toml` — the wire contract

Auto-generated by `mitos-build`; never hand-edited. Both the
module-side artifact bundle and the host-side admin API
exchange this shape so build-time and runtime see the same
metadata.

```toml
# Auto-generated by mitos-build. Do not edit.

[module]
id = "my-indexer"                                    # from --module or [package.metadata.mitos.id]
sha256 = "abc123def456..."                           # of the .wasm bytes
size_bytes = 2347832

[abi]
version_major = 1                                    # from module-version() export
version_minor = 0
wit_package = "mitos:platform"
wit_world = "mitos-module"

[trap_policy]
strategy = "replay"                                  # replay | skip-and-mark | quarantine
max_retries = 3
backoff_cap_ms = 1000

[build]
rust_version = "1.95.0"
target = "wasm32-wasip2"
profile = "release"
build_id = "2026-05-03T12:34:00Z"
git_sha = "abc123"                                   # if available
crate_version = "0.1.0"                              # from Cargo.toml
```

The host validates `version_major` against its `HOST_ABI_MAJOR`
(currently 1) at upload time and rejects mismatches. This
mirrors the Balius-PR-#98 problem we explicitly designed against
in `MITOS_PLATFORM_V1.md`.

### 3. `mitos-cli upload-module` — the deploy tool

Extends the existing `tools/mitos-admin/` (renaming to
`mitos-cli` if we're committing to it as the umbrella; otherwise
just adds a subcommand). Follows the same SSH/HTTP-talker pattern
already proven by `tools/capture-block/` and `tools/mitos-admin/`.

```bash
mitos-cli upload-module \
    --artifact target/mitos/my-indexer/ \
    --to https://mitos.example.com \
    [--config mitos.toml]
```

What it does:
1. Read `manifest.toml` from `--artifact`
2. Read `<module-id>.wasm` bytes
3. Optionally read `mitos.toml` (module config) — if present,
   serialised CBOR is included in the payload
4. POST `<base>/_admin/modules/<module-id>` with multipart:
   - `manifest` — TOML
   - `wasm` — application/wasm
   - `config` — application/cbor (optional)
5. Bearer auth via `MITOS_AUTH_TOKEN` env var
6. On 200: print activation summary + new sha
7. On 409 (conflict / already running same sha): print "no-op"
8. On 4xx/5xx: print structured error from the response body

Composability:

```bash
# Build then upload — what `wrangler deploy` does
mitos-cli deploy --to https://mitos.example.com
  ↓
  mitos-build --crate <auto>
  mitos-cli upload-module --artifact target/mitos/<auto>/ --to ...
```

`mitos-cli deploy` is a thin convenience that runs both halves;
power users can run them separately for CI/CD.

Other subcommands the CLI gets for free by extending
`mitos-admin`:

```bash
mitos-cli list-modules                     # GET /_admin/modules
mitos-cli get-module <id>                  # GET /_admin/modules/<id>
mitos-cli delete-module <id>               # DELETE /_admin/modules/<id>
mitos-cli restart-module <id>              # POST /_admin/modules/<id>/restart
```

### 4. Mitos host `/_admin/modules/*` routes

Server-side counterpart. Adds to mitos's existing axum
admin router (already serves `/_admin/subscriptions`); same
auth middleware, same TLS termination, same Cloudflare tunnel.

Routes:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/_admin/modules` | List registered modules + their state |
| `POST` | `/_admin/modules/{id}` | Upload + activate a new version atomically |
| `GET` | `/_admin/modules/{id}` | Single module status (running/quarantined/idle, last error, cursor, abi version, trap policy) |
| `DELETE` | `/_admin/modules/{id}` | Unregister + reclaim state (KV table, cursor row) |
| `POST` | `/_admin/modules/{id}/restart` | Restart the instance without re-uploading |

Upload flow on the host side:

1. **Auth** — same bearer middleware as `/_admin/subscriptions`.
   v2 will gate per-module ownership here.
2. **Receive** — multipart upload to a tempfile under
   `/var/lib/mitos/incoming/`. Cap size at e.g. 64MiB; reject
   anything bigger as a client error.
3. **Validate manifest** — TOML parse, check
   `[abi].version_major == HOST_ABI_MAJOR`. Reject on mismatch
   with a structured `AbiMismatch { wanted, got }` error
   payload (CLI surfaces this nicely).
4. **Validate wasm** — SHA-256 verify, then
   `Component::from_file` to confirm wasmtime accepts it. Then
   extract the world via wasmtime's component metadata API and
   confirm it matches `mitos:platform/mitos-module`.
5. **Dry instantiate** — fresh `Store` + `ResourceBudget`,
   call `module-version()` + `trap-policy()`, confirm the
   manifest's claimed values match the wasm's actual exports.
   Reject if they diverge — protects against tampered
   manifests.
6. **Activate atomically** — move artifact from
   `incoming/<sha>.wasm` to
   `/var/lib/mitos/modules/<id>/<sha>.wasm`. Update a
   per-module symlink `current.wasm` → `<sha>.wasm`. Atomic
   rename; readers see either the old or the new, never a
   partial write.
7. **Restart instance** — kill current `Driver` for this
   module-id, instantiate fresh against the new component,
   start a chain follower against it. Cursor persists across
   restart (via the future vendored `store.rs`); for now
   resumes from in-memory cursor or from configured start point.
8. **Respond** — 200 with the new sha, the started instance's
   `ChainPoint`, and a list of any subscriptions auto-rebound.

Failure modes have explicit shapes, all caught at validation
before activation:

- `AbiMismatch` — module declares wrong ABI major
- `WitMismatch` — module's WIT world isn't `mitos:platform/mitos-module`
- `ManifestDriftedFromWasm` — manifest claims trap-policy=replay but wasm exports skip-and-mark
- `WasmInvalid` — wasmtime can't parse the component
- `Quarantined` — previous instance was quarantined; refuses upload until manual `mitos-cli restart-module --force` clears the flag (avoids "redeploy as workaround for quarantine investigation")

## What we tap into

Reusable infrastructure we don't have to rebuild:

- **`tools/mitos-admin/`** — already implements the
  `MITOS_AUTH_TOKEN` + base URL + reqwest pattern. We extend
  its CLI surface rather than start from scratch.
- **`mitos-core`'s existing axum admin router** — auth
  middleware, error response formatting, JSON serialization.
  New routes plug in.
- **`wasmtime::component::Component`** — already used in
  `mitos-platform::ModuleRegistry::load_from_path` for the
  validation we need at upload time.
- **`mitos-platform::ModuleRegistry`** — the existing v1
  load + ABI handshake path is the activation primitive; we
  drive it from the upload handler instead of from a
  static-config startup.
- **`tools/capture-block/`** — pattern reference for tools
  that talk to the host over HTTP / SSH; same shape applies.
- **`shiku`** (at `~/code/defrag/augminted-bots/shiku/`) — not
  imported, but the mental model of `release upload` →
  `release activate <sha>` is the same. We implement it
  ourselves because mitos modules have a different lifecycle
  (hot-load into a running process, not systemd swap), but
  the CLI shape can mirror it.
- **Wrangler's split** — `worker-build` is the build tool,
  `wrangler deploy` is the deploy tool. Shape we copy:
  separate concerns, manifest as the wire contract, optional
  one-shot wrapper for ergonomics.
- **`wasm-tools component wit`** — for extracting the WIT
  world from a built component to validate against the
  expected world. Comes via Bytecode Alliance, no
  custom-decode work needed.

## Auth roadmap

V1: single `MITOS_AUTH_TOKEN`, same as today. Forward-compatible
URL shape (`/_admin/modules/<id>`) means v2 can layer
per-module ownership without breaking v1 clients.

V2 (when we onboard a second team or expose mitos as a managed
service):

- **Per-module owner identifier** stored in module config when
  registered. Today's bearer token implicitly owns everything;
  v2 introduces a `owner` field.
- **Per-team API keys** with scopes:
  - `module:upload:<id>` — can upload to a specific module
  - `module:upload:*` — can upload any (operator role)
  - `module:read:*` — can list/get any (read-only role)
- **Token issuance via a separate operator-only endpoint**:
  `POST /_admin/tokens` (gated by a master operator token).
  Issued tokens are JWTs or opaque hex; revocable via
  `DELETE /_admin/tokens/<id>`.
- **Audit log** — every module upload + activation logs to
  a per-module log file with token id, timestamp, sha, source
  IP. Required for the multi-team story.

V3 (further out): SSO / mTLS / OIDC for human users, machine
tokens for CI. Don't design for this now; just don't paint
into a corner.

The migration from v1 to v2 is non-breaking because the
URL shape and the manifest shape don't change. The auth
middleware swaps out; routes stay the same.

## Concrete delivery sequence

What to build, in order, each item shippable independently:

### Phase 1 — host-side admin routes (mitos repo)

1. **`POST /_admin/modules/{id}` upload+activate** — happy
   path only. Reuses `mitos-platform::ModuleRegistry`. Gated
   by `MITOS_AUTH_TOKEN`. Stores artifacts under
   `/var/lib/mitos/modules/<id>/`. Returns 200 with sha.
2. **`GET /_admin/modules` + `GET /_admin/modules/{id}`** —
   read-only state inspection. Powers `mitos-cli list-modules`
   / `get-module`.
3. **`DELETE /_admin/modules/{id}` + `POST .../restart`** —
   completes the lifecycle CRUD.
4. **Validation polish** — structured failure shapes
   (`AbiMismatch`, `WitMismatch`, etc.) with stable error
   codes the CLI can pretty-print.

### Phase 2 — `mitos-build` tool (mitos repo)

1. **MVP build path** — runs `cargo build`, validates with
   wasmtime, generates `manifest.toml`, writes artifact dir.
   No `[package.metadata.mitos]` autodetection yet — explicit
   `--crate` flag.
2. **Manifest schema crate** — `mitos-protocol::deploy` types
   so build tool, upload tool, and host all see the same
   shape (avoids the historical mirror-types drift problem).
3. **`[package.metadata.mitos]` autodetect** — if running from
   inside a configured workspace member, no flags needed.
4. **`--json` output** — for CI integration.

### Phase 3 — `mitos-cli upload-module` + `deploy` (mitos repo)

1. **`upload-module` subcommand** added to `mitos-admin`. Reads
   artifact + manifest, multipart-uploads, surfaces structured
   errors from the host.
2. **`deploy` subcommand** — chains `mitos-build` + `upload-module`
   into one ergonomic call.
3. **`list-modules` / `get-module` / `delete-module` /
   `restart-module`** — round out the CRUD CLI.
4. **Rename `mitos-admin` → `mitos-cli`** if we're committing
   to it as the umbrella. Backwards-compat shim for one
   release cycle.

### Phase 4 — companion-side orchestration (deferred)

Companion-half deploy still goes through wrangler, unchanged.
Future enhancement: `mitos-cli deploy --with-companion` runs
`wrangler deploy` after the module upload succeeds, with
ordering guarantees (companion ready before module starts
emitting). Out of v1 scope.

### Phase 5 — multi-user auth (when needed)

Triggered by: second team onboards OR managed-mitos service
launches. See "Auth roadmap" above for the migration shape.

## Resolved design questions

These were originally open; user feedback (2026-05-03) settled
them. Recorded here so the rationale is recoverable.

### 1. Artifact storage layout — RESOLVED: per-sha files + symlink

```
/var/lib/mitos/modules/<id>/
  current.wasm            → <active-sha>.wasm   (symlink)
  <sha-1>.wasm            (rollback target)
  <sha-2>.wasm            (rollback target)
  <sha-active>.wasm       (current)
  manifest.toml           (matches current)
  state/                  (per-module redb dir; cursor + KV)
  quarantine.toml         (only present when quarantined; see #3)
```

Atomic activation: write `<new-sha>.wasm`, `ln -sf
<new-sha>.wasm current.wasm.tmp`, `mv current.wasm.tmp
current.wasm`. Readers see either old or new, never partial.

Rollback (`mitos-cli rollback <sha>`) is trivial: re-point
`current.wasm` at any historical sha that's still on disk. Old
shas get pruned by a future `mitos-cli prune-modules
--keep-last N` (defer until disk pressure becomes real).

### 2. Cursor handling on upload-replaces-running — RESOLVED: resume

The new instance picks up the cursor where the old one left
off. Idempotent dispatch is already a v1 contract for `replay`
modules; for `skip-and-mark` and `quarantine` modules the
cursor reflects the last successfully-processed block, so
resuming is safe regardless of trap policy.

`--reset-cursor` flag is available as an escape hatch (drops
the persisted cursor + restarts from configured start point);
defaults to off. Useful when the module's emit shape has
changed in a way that requires a clean re-derivation of state
on the consumer side.

### 3. Quarantine clearing — RESOLVED: prove-by-replay

Sharper version of "manual `--force` only": when an upload
arrives for a quarantined module, the host **doesn't blindly
swap**. It instead activates the new component in **validation
mode** and replays the block that triggered the quarantine. If
the new code processes that block successfully, it takes over
and the quarantine clears; if it traps again, the upload is
rejected with the new error and the existing quarantine
stands.

State machine:

```
[running] ──trap-policy=quarantine + N consecutive failures──> [quarantined]
[quarantined] ──upload arrives──> [validating]
[validating] ──new module passes failing block──> [running] (active sha = new sha)
[validating] ──new module also traps──> [quarantined] (active sha unchanged, error logged)
[quarantined] ──upload --force──> [running] (skip validation; operator override)
```

Implementation requirements:

- **Quarantine state persists.** When supervisor decides
  `Quarantine`, write `quarantine.toml` next to `current.wasm`:
  ```toml
  failing_slot = 186000000
  failing_block_sha = "..."           # so we can detect block reorgs
  last_error = "..."
  trapped_at = "2026-05-03T12:34:00Z"
  consecutive_failures = 5
  ```
- **Block re-fetch.** Validation mode reads the failing block's
  CBOR from the local dolos archive (same path
  `capture-block` uses). If the slot's no longer in the
  archive (rolled past retention), validation falls back to
  "best-effort" mode that just runs the new module against
  recent blocks instead — not as strong a proof, but better
  than nothing.
- **Sandboxed validation instance.** New `Driver` built with
  the new component, a fresh `ResolvedBlock` for the failing
  slot, fuel + epoch budgets at v1 defaults. Single
  `apply_cbor` call. Outcome:
  - `Applied` → activation succeeds, swap symlink, transition
    to running, clear `quarantine.toml`
  - `Skipped` → activation succeeds (the new module declared
    `skip-and-mark` and skipped the failing block; that's a
    valid resolution)
  - `RestartedRetry` → run the inner re-feed loop once more
    (max retries hit by the new module's policy = treat as
    failed validation)
  - `Quarantined` → activation refused; respond 422 with
    `{ ok: false, validation: { slot: ..., error: ... } }`
- **`--force` escape.** Skips validation entirely, swaps
  symlink, clears quarantine. Logged loudly. For when the
  operator knows the module fix doesn't depend on processing
  the failing block (e.g. config schema change).

This shape is much sharper than v1's original "refuse without
`--force`" because:

- It catches the "fix doesn't actually fix it" case
  automatically — no more "deployed, looked green, hit the
  same trap on the next chain event" surprises
- The audit trail is structured (validation result, not just
  "operator forced an override")
- It's the natural interpretation of what `replay` means:
  prove the new code handles the data the old code couldn't

### 4. Concurrent uploads — RESOLVED: 409 on race

Per-module lock acquired at the start of upload validation,
released after symlink swap. Second uploader's request returns
`409 Conflict { in_progress: true, started_at: ... }`. CLI
prints "another upload is in progress; retry shortly."

Lock is a tempfile (`/var/lib/mitos/modules/<id>/.upload.lock`)
with the pid + start timestamp. Stale locks (older than 5m)
get reaped on the next attempt — protects against crashed
upload handlers leaving the lock orphaned.

### 5. Config-only updates — DEFERRED to v2

V1: every config change ships with a fresh wasm artifact. The
build is fast (`cargo build --target wasm32-wasip2 --release`
of a small indexer crate is sub-30s incremental), so the
ergonomic cost is low. If teams hit this in practice — e.g.
operator wants to add a new watched policy without rebuilding
— add `POST /_admin/modules/{id}/config` then.

### 6. Build reproducibility — DEFERRED

Wasmtime's component layout has non-determinism (build
timestamps in custom sections, allocation patterns affecting
order). Not promising bit-identical rebuilds in v1; the
manifest's sha is "we got this exact bytes," not "anyone can
rebuild this."

If reproducibility becomes important later (supply-chain audit,
managed-mitos service trust model), the path is well-trodden:
`SOURCE_DATE_EPOCH=0`, deterministic `cargo build`, `wasm-tools
strip` to remove non-deterministic custom sections. Worth
doing then; not worth the complexity now.

### 7. Vendoring Balius's `store.rs` — RESOLVED: don't, build focused redb cursor instead

Originally listed as planned vendoring (alongside `kv.rs`,
`router.rs`, `metrics.rs`) per `MITOS_PLATFORM_V1.md`'s "What
we vendor from Balius" section. On closer inspection, the file
isn't a fit for our v1 needs.

**What Balius's `store.rs` actually is:** a write-ahead log for
replay-safe worker restart. Two redb tables:
- `CURSORS`: `WorkerId → LogSeq` (each worker's position in the WAL)
- `WAL`: `LogSeq → LogEntry { next_block, undo_blocks }`

On worker restart, Balius replays from the worker's recorded
`LogSeq` forward through the WAL — that's how a Balius worker
catches up after a crash without re-fetching from chain.

**Why mitos doesn't need this:** dolos's archive *is* our WAL.
On module restart we re-subscribe via
`Domain::watch_tip(Some(persisted_cursor))` and dolos serves
the missed blocks directly from its archive. A host-side WAL
would be a duplicate retention layer with no behavioural
benefit.

**What we built instead:** a focused single-row `CursorStore`
in `mitos_platform::storage`:
- One redb file per module: `<storage>/<id>/cursor.redb`
- One table `cursor` with one row keyed `"current"`,
  value=CBOR-encoded `ChainPoint`
- Open/write/commit/close per call (cursor writes are
  infrequent — one per applied block — so the open cost is
  negligible compared to the block dispatch cost)

This gives us crash-safety (atomic redb commit, fsync on close)
without the operational complexity of a host-side WAL. Roughly
80 lines vs. Balius's 252.

**KV side** (the other half of "module state"): the existing
`vendored/balius/kv.rs` continues to back per-module KV via
`ModuleKv::open_redb(<storage>/<id>/kv.redb)`. The bundle's
KV factory builds these per-module on first use; falls back
to in-memory with a loud error log if redb open fails (avoids
host startup failure for a single bad module).

**Updating the vendoring plan in `MITOS_PLATFORM_V1.md`:** the
list of "planned vendorings" loses `store.rs`. `router.rs` +
`metrics.rs` remain on the plan for when we actually need them
(router: when modules declare typed Watch sets at init-time;
metrics: when OpenTelemetry surfaces are wired into the host).

## Lessons banked from related work

- **`worker-build` does ONE thing well** (build a wasm-bindgen
  Rust crate into a CF Workers-compatible artifact). Wrangler
  does the deploy. Don't merge them. Same lesson here:
  `mitos-build` and `mitos-cli upload-module` stay separate.
- **wasmtime's component validation is exhaustive** — let it
  do the work. Don't try to hand-roll a wasm sanity-checker.
  The only wrapper we add is "pretty-print the failure to a
  user."
- **Mirror-types drift is a recurring footgun** in the cnft.dev
  stack (memory bank: "Mirror types are a recurring footgun.
  The OwnershipChange mirror in the worker has caused at least
  two bugs"). Prevention: the manifest shape lives in one
  shared crate (`mitos-protocol::deploy`); build tool, deploy
  tool, and host all consume it. No hand-mirrored copies.
- **Atomic activation matters** — the symlink-swap pattern
  (write new file, rename over symlink) is the right shape;
  half-written artifacts are a real failure mode in production.
  Same pattern shiku uses for systemd swap; we apply it to
  hot-load.
- **"Refuse and surface" beats "fix silently"** — quarantine
  blocking redeploy without explicit `--force` prevents
  redeploy-as-debugging-tool, which is how broken-and-stays-broken
  modules happen in practice.
